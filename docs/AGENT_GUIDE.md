**思维链（可复用的推理路径）**

1. **拆两层**：问题一不含实体机与电池调度 ⇒ 先解"单点往返能带多少"（载荷），再解"怎么把 80 箱装进最少架次"（装箱）。
2. **载荷层**：`L_g(q) = L_g0 − (L_g0 − L_gF)·(q/Q_g)^{3/2}` 单调不增；往返能耗约束 `E_g^T(q) ≤ (1−ρ_g)·E_g^use`。
   `(q/Q_g)^{3/2}` **无初等反函数** ⇒ 必须**数值反解**（Brent 法，`[0, Q_g]` 上单调）。
   安全载荷 = `min(能量反解值, Q_g, 体积瓶颈对应质量)`。
   → **结论**：A 型 15/15 受**结构**约束（恒 25 kg），B 型 14/15，C 型仅 10/15（远距离时能量才成紧约束）。
3. **装箱层**：货箱不可拆 + 恰用一次 + 质量/体积/能量三约束 ⇒ **质量—体积二维装箱**。
   ★ **当前答案用精确 DP，不用 FFD**：先把同 (质量, 体积, 首批标记, 期望时间) 的箱**聚合为箱型**
   （每区仅 3~5 型），再对每个 (服务区, 机型) 枚举**可行批次**，最后在箱型计数状态上做
   **字典序 DP** `min_lex(#架次, 能耗, 累计作业时间)`。FFD（体积降序、首次适应）仅作对照基线。
4. **最优性**：`sortie_lower_bound()` 给出**质量下界 / 体积下界**（都在**能量可行的机型**上取最大容量，见 ADR-034），取大者。
   精确 DP **逐服务区等于下界**（15/15 区差距为 0，下界合计 18）⇒ 架次数维度**可证最优**；
   这是本题最有力的"质证"。**注意**：该下界对二维可行性**不完备**，只能说"逐区相等 ⇒ 该实例上下界是紧的"。
5. **敏感性（P10b 起与答案路径同口径）**：`q1_4_rho_sweep.csv` 扫描 ρ ∈ {0.10, 0.20, 0.30, 0.40, 0.50}，
   **每个取值都用精确字典序 DP 重跑组批**（`sweep_reserve_ratio_exact`，`strategy` 列固定为 `exact_dp`）：
   ρ=0.10 → **18 架次 / 59.087498 kWh / B:9+C:9**；ρ=0.20（附件值）→ **完全相同**；
   ρ=0.30 → 20 架次 / 67.180487 kWh / B:9+C:11；
   ρ=0.40 起 `feasible=False`（**2 个区**无可行组批）、ρ=0.50 时 **5 个区**。
   ⇒ **正确读法**：ρ_g ∈ [0.10, 0.20] **不损失任何效率**（组批受体积/结构约束、不由能量决定），
   不可行从 **0.40** 才开始；附件取 0.20 留有充分裕度。
   ⚠️ 启发式版本另存 `q1_4_rho_sweep_heuristic_ref.csv`（ρ=0.20 给 75.070591 kWh，全 C 型），
   **只是策略集合的对照，不得进论文表格**（`build_paper.py` 亦如此约定）。
   ★ 同组批改全 C 型的对照（18 架次 / **74.2611 kWh**）来自 `q1_3_strategy_comparison.csv`，
   与扫描表是两回事：前者是"仅换机型"，后者是"改返航余量后重新组批"。

**思维链**

1. **新增三类耦合**：① 多点串飞 ⇒ 载荷**逐段递减**；② 机型异构 ⇒ 容量/速度/能耗不同；③ 共享电池 + 两阶段充电 ⇒ 资源周转成为瓶颈。
2. **多点串飞模型**：设访问顺序 `(S_a, S_b, …)`，第 m 段机载荷 = **尚未投送货箱之和**。
   前缀可行性：`∀m: Σ_{k≥m} m_k ≤ Q_g` 且 `Σ_{k≥m} v_k ≤ V_g`（下标是"从第 m 站起仍留在机上的货"）。
   架次能耗 = **逐段求和** `Σ_m E_g(seg_m, q_m)`（★ 不能拿总距离当一段，见初稿错误 #3）。
   架次时间 `t_p = t_prep + n_box·t_load + Σ_m t_g(seg_m) + Σ_站(t_h0 + k_s·t_h1)`（★ 交接时间逐站累加，见初稿错误 #5）。
   ★ 本方案的 23 个架次**全部是单点路线**，故"多点串飞"与"载荷递减"在本轮结果里不激活
   （它们仍是模型的一部分，且是 Q4 原子单元的来源）。
3. **求解框架（现行）"精确组批 → 时限驱动拆分 → CP-SAT 区间调度 → 独立校验"**：
   - **组批**：11 个区直接用 Q1 的精确字典序 DP 组批；S006/S007/S008/S013 保留为满足首批/医疗时限的"先行小架次 + 余量架次"拆分（18→23）；
   - **交付耗时**：由本仓物理层 `compute_delivery_offset()` 重算（准备 + 逐箱装载 + 飞行），**不采信**权威数据 `delivery` 字段当耗时（该字段含义不一致）；
   - **调度**：CP-SAT 联合决定 `(实体机 u_r, 共享电池 k_r, 起飞时刻 t_r)`，最小化 `max_r(t_r+d_r)`；
     实体机与电池各一条 `NoOverlap`，电池占用含两阶段充电周转，`t_r + τ_r ≤ 首批截止 / 期望送达`；
     把已知可行调度注入为 hint，避免分支定界"证明"一个比已知可行解更差的 OPTIMAL（ADR-035）；
   - **最优性**：另做**独立探针** —— 逐档收紧 `Cmax` 上界做可行性判定（见上文对比结论）。
4. **机队必须整体投入（本题最关键的认识）**：题目给的是 **异构机队 A×4+B×2+C×2=8 架**。
   本方案使用 **A 型 6 个架次 + B 型 9 个 + C 型 8 个**（8 架实体机全部投入、**14 组电池**），
   **瓶颈是电池周转**：把电池减半或把实体机减到 4 架，CP-SAT 直接返回 INFEASIBLE。
   - **不要**再写"首批时限物理不可行"（那是"只用 2 架 C 型"的旧求解器产物）。

2. **通信判定三要素**：地形遮挡（沿视线水平投影采样，比地面高程与视线插值高度；遮挡**只附加 10 dB**，不直接判中断）

5. **降维技巧（可复用）**：中继选址本是连续三维变量，逐时刻独立选址会退化成难解的连续最优控制。

   属旧管线的探索层，**不在现行报告链中**。

**思维链**

1. **识别硬规则**：题目规定"**同一运输架次涉及的服务区必须划入同一组**" ⇒ 服务区之间产生**等价关系**
   ⇒ 问题自然建模为**图 + 连通分量**，每个连通分量是一个**不可拆原子单元**。
2. **求连通分量**：对问题三方案的 **23 个架次**构图。★ 本轮**没有多点架次**
   （`n_multi_stop_sorties = 0`）⇒ 图上没有任何边 ⇒ 得到 **15 个连通分量**（每区一个）。
   ★ **先求分量、再对分量划分**：若先对 15 个服务区直接枚举或聚类，
   虽然在本轮（单位元）不会出错，但一旦 Q3 出现多点串飞就会产生违反规则的方案 —— 顺序不能颠倒。
3. **判定可行性（本题核心结论）**：K 个组要求把图切成 K 个分量 ⇒ 合法组数 **K ∈ [1, 15]**
   （每个单元不可再拆、多个单元可合并成一组）⇒ **K=2 与 K=3 均可直接由单元合并得到，改动 0 个架次**。
   ★ **分量数由问题三方案的多点串飞结构决定**（本轮为 15，历史上曾为 5 / 3 / 1），
   跑完 Q3 必须用 `check_paper_numbers.py` 复核，**不要硬编码**。
4. **找桥接架次**：逐条试"移除该架次后分量数是否增加" ⇒ 本轮 **0 个桥接架次**
   （单点架次本身不连接任何两个服务区）。桥接清单的用途不变：
   作为**进一步细化分区粒度的备用依据**（每拆一个桥接架次可多得到 1 个可选分组粒度）。
5. **资源核算（组内独立、不得跨组调配）**：
   - 运输机/电池：按组内架次的**时间区间求并行峰值** `_parallel_peak`（★ 注意**首尾相接不算重叠**，
     排序键要用 `(t, delta)` 让 −1 先于 +1，否则会虚报"缺 1 架"）；
   - 电池组数 `batteries_required`：考虑充电周转；
   - 中继机/能源组件：★ **先做唯一归属**（`assign_relays_to_groups`，归给覆盖架次最多的组），
     再按 `group_resources(..., owned_relays=...)` 同法核算 —— 不做归属会让任何真分组都认领不到中继（ADR-037）。
6. **对比与结论**：K=1/2/3 ⇒ 资源总量 **28/29/30（台·组）**、不均衡度 **0/0.2289/0.8425**、
   单组最大工作量 **11.27/6.28/5.62 h** ⇒ **分区要额外储备运输机峰值（8→9→10 架），
   但能把单组作业压力降约 50%**。这对"多支救援队同时作业、各自独立补给"的现场组织方式有利，
   是一条**有工程指导意义的结论**。
7. **资源缺口（`q4_资源缺口.csv`，逐项 = 需求 − 库存）**：
   - **K=1**：运输机 A4/B2/C2、电池 A6/B4、中继机 2 架**恰好够用**、中继能源组件冗余 3 组；
     **唯一缺口是 C 型电池 +1 组**（需求 5 / 库存 4）；
   - **K=2**：**B 型运输机 +1 架**（需求 3 / 库存 2）**且 C 型电池 +1 组**；
   - **K=3**：**B 型运输机 +1 架、C 型运输机 +1 架**（需求 3 / 库存 2）**且 C 型电池 +1 组**；
     A 型机与 A/B 型电池、中继机、中继组件均不缺。
   ⚠️ 表述缺口时**按机型逐项写**（`q4_资源缺口.csv` 是唯一依据）；
   不要写成笼统的"A 型缺 2 架"之类 —— 该口径属旧管线结论，本轮不成立。

   否则用 pandoc 默认样式（标题非中文习惯字体）。
3. `--toc --toc-depth=2` 生成两级目录。
4. 校验：`python scripts\diag\check_pandoc_docx.py <docx> [out.pdf]`
   —— 会报告 `m:oMath` 数、Word 页数、并调 `OMaths(1).BuildUp()` 证明公式是
   **原生可编辑**对象（而非图片或纯文本）。
5. 结构对比：`python scripts\diag\docx_struct_stats.py <docx>...`
   —— 一眼看出公式/标题/表格/图片数与样式数。

> ⚠️ pandoc 转换**不做**竞赛排版控制：没有章页分页、题注与图不同页的约束，
> 表宽/浮动体位置也与 LaTeX 原稿不同。**公式版用于核对公式，正式提交仍用
> Python 管线那一份**；若要合并两者，请以提交稿为骨架、只把公式替换为
> pandoc 产出的 OMML（后者已证明可 `BuildUp`）。


### 4.3 三份论文产物对照（别搞混）

| 产物 | 生成方式 | 公式 | 可编辑 | 页数 | 入库 |
|---|---|---|---|---|---|
| `paper/…_论文.docx` + `.pdf` | Python 管线 `src/report/build_paper.py`（**正式提交稿**） | 106 个 OMML | ✅ | 53 | ❌ 已移除，本地保留 |
| `paper/…_论文_LaTeX公式版.docx` + `.pdf` | **pandoc** 转 `otheragent/document.tex`（**公式基准版**） | **554 个原生 OMML** | ✅ | 75 | ❌ 已移除，本地保留 |
| `paper/…_论文_PDF转Word.docx` | Word 自带 PDF 重排（分块）转 `document.pdf` | **图片**（公式编号保留） | ❌ | 71 | ❌ 已移除，本地保留 |
| **`paper/…_论文_PDF转Word_pdf2docx.docx`** | **pdf2docx** 转 `document.pdf` | 文本/图片 | ❌ | — | ✅ **唯一在库** |

> **仓库策略**：按要求只保留 pdf2docx 那一份入库，其余已在 `.gitignore` 中屏蔽
> （避免 `git add -A` 又带回来），但**仍保留在本地磁盘**，且可从 git 历史取回。
> 重新生成命令见 `.gitignore` 内注释与 `docs/PDF_TO_WORD.md`。

**关键结论：从 PDF 转出的 Word，公式一定是图片** —— PDF 里公式已是矢量字形、
语义结构已丢失，任何工具都无法还原成可编辑公式对象（实测 Word 重排与 pdf2docx
的 `m:oMath` 均为 **0**）。要"可双击编辑的原生公式"，**只能从 LaTeX 源转**（pandoc）。

**为什么 PDF 转换要分块**：整本 56 页一次性交给 Word 重排会崩（`RPC 服务器不可用`）
且极慢（3 页 274 s，含 Word 冷启动）；**按 4 页切片后单片约 15 s，全量约 8 min**，稳定成功。
另有两个必踩的坑：Word COM **不继承进程 cwd**（相对路径会被解析到
`C:\Windows\system32`，必须 `.resolve()` 成绝对路径）；**切片进行中不要清理切片目录**，
否则 Word 会卡死在模态对话框上（表现为 WINWORD 进程 CPU 停在个位数、任务永不返回）。
完整三路径对比与 5 条踩坑见 **`docs/PDF_TO_WORD.md`**。
