# 实现计划（IMPLEMENTATION PLAN）— 物理层与地理层

> 本文件是 P0b / P1 的实现蓝图。**分层解耦是本计划的第一原则**：
> 每层只依赖其下一层，且**下层不得反向依赖上层**。
> 任何跨层调用都必须经由明确的接口（Protocol / 纯函数）。

---

## 1. 为什么要分层解耦（本题的具体痛点）

| 痛点 | 若不接耦会怎样 |
|---|---|
| DEM 采样慢（1486×1309 栅格） | 每算一次能耗都读栅格 → Q2/Q3 求解器跑不动 |
| 经纬度坐标 | 各处自己写投影代码 → 单位混乱、结论互相矛盾 |
| 公式口径必须四处一致（铁律 R4） | 各问各写一份 → 四问结果对不上，直接失分 |
| 单元测试需要**不依赖真实数据** | 耦合后测试必须带 7.5 MB DEM 才能跑 |

**解耦收益**：物理公式可用**解析高程函数**测试（不碰 DEM），
DEM 的真实读取只在 `geo/` 层发生一次并被缓存。

---

## 2. 分层结构（严格单向依赖）

```
┌─────────────────────────────────────────────────────────────┐
│ L4  问题层   q1_payload_grouping / q2 / q3 / q4             │
│     只做"决策"，不碰公式；全部物理量向 L3 索要                  │
└───────────────────────────┬─────────────────────────────────┘
                            │ 只依赖 ↓
┌───────────────────────────▼─────────────────────────────────┐
│ L3  领域层   physics/  comms/  verify/                       │
│     physics: 载荷-航程、能耗、电池、架次汇总                    │
│     comms:   链路预算、三态判定                                 │
│     verify:  独立可行性校验器（不许调用 L4 的求解器）             │
└───────────────────────────┬─────────────────────────────────┘
                            │ 只依赖 ↓（关键解耦点）
┌───────────────────────────▼─────────────────────────────────┐
│ L2  几何层   geo/leg.py                                      │
│     把 (节点, 高程) 变成 (d, h+, h-, cruise_alt)               │
│     ★ 通过 ElevationProvider 协议拿高程 —— 不直接读 DEM         │
└───────────────────────────┬─────────────────────────────────┘
                            │ 只依赖 ↓
┌───────────────────────────▼─────────────────────────────────┐
│ L1  基础层   geo/crs.py   geo/dem.py                         │
│     crs: 经纬度 → 米制投影（唯一入口，ADR-011）                  │
│     dem: 栅格读取 + 双线性采样 + 沿线最高点；实现 Provider      │
└───────────────────────────┬─────────────────────────────────┘
                            │ 只依赖 ↓
┌───────────────────────────▼─────────────────────────────────┐
│ L0  数据/常量层   common/config.py   q0_data/                 │
│     路径、SEED、题目常量、附件解析与建模接口                      │
└─────────────────────────────────────────────────────────────┘
```

**★ 关键解耦点：`ElevationProvider` 协议**

```python
class ElevationProvider(Protocol):
    def elevation_at(self, lon: float, lat: float) -> float:
        """返回该经纬度处的地面海拔（m），越界抛 OutOfBoundsError。"""
```

- `geo/dem.py` 提供一个**基于 rasterio 的真实实现** `RasterElevationProvider`
- `tests/` 提供**解析实现** `AnalyticElevationProvider`（如 `z = 100 + 0.001*x`）
- 于是 `physics/` 与 `geo/leg.py` 都能**脱离 DEM 做单元测试**

### 已完成部分的验证结果

- **101 项测试全部通过**（含 3 项读取真实 DEM 的对照测试）
- 真实数据冒烟（`scripts/smoke_physics_real_data.py`）：
  - 单向距离 2808 ~ 8079 m，巡航海拔 271 ~ 586 m
  - 三种机型在全部 15 个服务区**均可行**（无超能量情况）
  - **A 型 15/15、B 型 14/15、C 型 10/15 个服务区受结构上限 `Q_g` 约束**，
    仅 S002/S003/S004/S008/S012 对 C 型构成能量约束
  - `q_max` 反解的能量约束**取等号**（相对偏差 5.6e-15）

> **重要含义**：单点往返场景下**结构载重是主要瓶颈，能量是次要约束**。
> 这会显著影响 Q1 组批方案的形态（详见 `docs/MODEL_NOTES.md`）。

## 5. 必须锁死的公式（来自附件实测）

| 项 | 公式/值 | 来源 |
|---|---|---|
| 载荷-航程 | `L_g(q) = L_g0 − (L_g0−L_gF)·(q/Q_g)^{3/2}` | 题目附录 2 |
| 巡航海拔 | 航段经过 DEM 像元**最高地面高程 + 50 m** | 题目附录 2 |
| 作业高度 | O01 = 地面海拔；服务区 = 地面海拔 + 30 m | 题目附录 2 |
| 航段时间 | `h⁺/v↑ + d/v_c + h⁻/v↓` | 题目附录 2 |
| 航段能耗 | 水平巡航 + 爬升附加；**下降效率 = 0** | 附件确认 |
| 返航余量 | `E_p^T ≤ (1 − 0.20)·E_g^use` | 附件 `ρ_g = 20%` |
| 充电 | `s<0.9`: `T_full[0.65(0.9−s)/0.9 + 0.35]`；`s≥0.9`: `T_full·0.35(1−s)/0.1` | 题目附录 2 |
| FSPL | `32.45 + 20log₁₀f(MHz) + 20log₁₀D(km)` | 题目附录 3 |
| 双向门限 | `min(L_max,a→b, L_max,b→a)` | 题目附录 3 |
| 天线增益 | `G_t = G_r = G`（附件只给一列） | ADR-018 |
